AI Hackathon · Use Case 4 · Line Engineer Agent · Complete design v4

LineReady: complete system design

A multi-agent assistant that prepares every defect before the engineer reaches the aircraft. This document covers what it does, how people use it, the agent design, memory, knowledge base, retrieval, review layer, token budget, and a free, self-hosted stack.

At a glance Code does what code can. Claude does the rest. Every line is reviewed and cited.

About 70% of a shift brief is facts (open defects, deadlines, stock, sector counts), and these come from SQL and rules at zero token cost. AI agents handle only the parts that need language: grouping symptoms, matching history, finding the manual task, and writing a short summary. Claude, through the Claude API, does the language and reasoning work. Everything else (database, embeddings, reranker, agent framework, UI) is free and open source.

4 · Multi-agent architecture

A hybrid of six proven patterns

No single pattern fits. A brief must be the same every time it is replayed, which suits a fixed workflow. Questions are open-ended, which suits a router with tool-using agents. Safety needs a critic and a human. LineReady combines six patterns, each used where it fits best.

PatternWhere we use itWhy
1 · Event-driven triggerT-60 schedule, new AVIATAR fault, new PHA case, user questionThe agent works one step ahead without being asked
2 · RouterThe entry node classifies the request (brief, dossier refresh, question, coach) and sends it to the right graphEach request takes the cheapest correct path
3 · Hierarchical supervisorShift Orchestrator → specialist agentsClear ownership. Specialists run in parallel.
4 · Plan-and-execute DAGThe brief pipeline is a fixed graph of stepsRepeatable and auditable. The same input gives the same plan.
5 · Blackboard (shared state)The dossier object. Each specialist writes only its own typed section.Agents share information without long chat threads, which saves tokens
6 · Reflection (critic loop) + human in the loopThe verifier checks and returns a draft at most once. Then a human reviews it.Accuracy, with people in control

5 · Memory

Yes, both: short-term for the current task, long-term for what it knows

Short-term memory holds the current task and is cleared when the task ends. Long-term memory is split by kind of knowledge, and each kind has its own write rules. Agents never write to long-term memory directly. Only the review layer and the learning gate can.

6 · Knowledge base design

Four stores, and each piece of data goes in the store that fits it

Structured data is never embedded. Text is embedded only when it is searched by meaning. Relationships live in a graph so they can be followed step by step. All four stores are in one Postgres database, which keeps the system simple.

Store A · relational

Facts

aircraft, work_order, wo_action, fault_event, episode, pha_case, stock_lot, tool, flight, roster, deferral, tsm_fault_index, manual_task. Answers "what, when, how many" with SQL.

Store B · graph (edges table)

Relationships

edge(src_type, src_id, rel, dst_type, dst_id, source_ref). Relations: HAS_DEFECT, SHOWS_MSG, INDEXED_TO (msg→TSM), REFERS_TO (TSM→AMM), REQUIRES_PART, REQUIRES_TOOL, STOCKED_AS, SIMILAR_TO. Traversed with recursive SQL, so no Neo4j is needed.

Store C · documents + vectors

Searchable text

chunk(id, doc, doc_rev, ata, task_id, parent_id, effectivity, approved, header, text, tsv, embedding). HNSW vector index plus a GIN full-text index on the same row.

Store D · memory

Learned and session state

aircraft_card, engineer_profile, case_outcome, playbook, session, feedback_ledger, audit_event (hash-chained).

-- every chunk carries the metadata needed for hard filters and citations
CREATE TABLE chunk (

7 · Chunking, embeddings and vectors

Yes, but only where meaning-based search helps

Each source gets its own chunking strategy. Manuals are split by their own structure, not by a fixed token count, so a step never loses its warning and a task is never cut in half.

Contextual header

Each chunk knows where it is

Before embedding, each chunk gets a short header such as TSM · 32-42 Braking · Task 32-42-00-810-923 Brake overheat · rev 2026-11-01. This fixes the most common failure, where a chunk reads "do step 3" with no subject.

Abbreviation expansion

Normalise before embedding

The text "RH ENG BLEED VLV" is indexed alongside its expanded form, "right engine bleed valve". The lexicon is mined from the logbook corpus, so lexical and meaning-based search both match.

Model

BGE-M3 (free, MIT)

1024-dimension dense vectors, an 8k-token input window, and an optional sparse output. Runs on CPU or a small GPU. Fallback for weak laptops: bge-small-en-v1.5 (384-dim).

Vector store

pgvector with an HNSW index

Lives in the same Postgres as everything else, so a single query can combine filters, full-text and vectors. If the data grows, Qdrant (Apache-2.0) is a drop-in swap behind the Retriever port.

Scope control: AMM and IPC together are 3.3 GB. For Round 1, embed only the ATA chapters in the demo night (for example 21, 32, 34, 49). Embed the rest in an overnight batch later.

10 · Token reduction

Ten ways to keep the LLM workload small

Fewer tokens means lower Claude API cost and faster briefs. The figures are design targets per defect dossier, to be measured in the build. Rough cost at Claude Opus 5.5 prices ($4 input / $20 output per million tokens): about 4k input + 500 output tokens is roughly $0.03 per dossier, so well under $1 for a 3-engineer brief.

Naive RAG (dump history + manuals)
~40,000
LineReady target
~4,000
#TechniqueHow
1Deterministic firstDeadlines, sector counts, stock and the fault index come from SQL and rules. No tokens.
2Template renderingThe UI renders facts from data. The LLM writes only a 1–2 sentence summary per item.
3Pre-aggregation376k fault rows → episodes. Hundreds of WOs → a 300-token aircraft memory card.
4Top-k + compressionRerank to the top 5, then pass only the matching sentences plus the IDs, not whole chunks.
5Reference by IDClaims point at evidence_ids instead of quoting text. The UI expands them.
6Short schemasCompact JSON keys, no prose fields, and a max_tokens limit on each agent.
7Effort routingOne model (claude-opus-5-5), with effort set per job: low for router and extraction, medium for specialists, high for the critic and Ask. Using one model also means one prompt cache.
8Incremental rebuildEach dossier is cached by a hash of its inputs. Only changed dossiers are rebuilt.
9Semantic + prefix cachingRepeated questions are answered from our own cache. Claude prompt caching covers the stable prefix (system prompt, tool definitions, aircraft card), and cached reads cost about 5% of normal input. Keep timestamps and request IDs after the cached part.
11Batch APIThe nightly learning agent, outcome labelling and the TSM backtest run through the Message Batches API at 50% of the normal price.
10Conversation summaryAsk keeps the last 6 turns plus a rolling summary, not the full history.
11 · Self-learning

It learns from engineers and from aircraft outcomes, and every change is reviewed

Model weights never change in production. Learning goes into versioned memory, and each change must pass the evals and get Quality approval.

Novel

Fix-outcome memory

After a work order closes, the system checks AVIATAR to see whether the fault came back within N sectors. The aircraft's own data shows which fixes worked. This is closed history, not prediction.

Retrieval weights

Citations that engineers open and use get a higher rank. Ones they dismiss get a lower rank.

Lexicon

Unmatched terms become proposed abbreviations for review.

ATA playbooks

Checks that senior engineers keep adding become standard dossier steps.

Curriculum

Common trainee gaps become targeted Coach questions.

12 · Clean architecture

Ports and adapters

The domain and rules are pure code. Agents depend on ports (interfaces), not on Excel files, Postgres or a specific model. File adapters can be swapped for live AMOS and AVIATAR APIs, and a local model for a hosted one, without touching business logic.

13 · Free resource stack

Claude API for reasoning, free open source for everything else
